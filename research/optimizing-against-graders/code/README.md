## Trainer (`train.py`)

```bash
.venv/bin/python train.py --arm A0 --state D1 --seed 0 --steps 5000000 --envs 3        # pilot (§9)
.venv/bin/python train.py --arm A2 --state HA --seed 0 ...                             # oracle
.venv/bin/python train.py --arm A1 --round 1 --proxy '{"tile_visit_cap": 600}' ...     # a patched round
.venv/bin/python train.py --resume A0-D1-s0                                            # after a crash or preemption
.venv/bin/python train.py --arm A0 --smoke --steps 20000                               # no start state needed
```

- **Outputs:** everything goes to `~/roms/runs/<run_id>/`: `config.json` (all settings, reward hash, versions), `metrics.jsonl` (per update), `episodes.jsonl` (per episode: P, T, milestone steps, hacks), rolling `ckpt-<step>.pt` (last 3), permanent `eval-<step>.pt` at 0.25M, 0.5M, 1M, 2M, …, and the closing eval frame `<run_id>.png/.json` (§10.6).
- **Checkpoints:** written every 15 min, on SIGTERM/SIGINT/SIGHUP, and at exit. Each goes to a temp file and is then renamed. `--resume` restores weights, optimizer, step counters and RNG states; episodes in progress restart from the start state.
  - **SIGHUP (fixed 2026-11-03):** on VM shutdown tmux sends SIGHUP, whose default action killed the trainer before its `finally:` checkpoint. So the pilot's resumes came from the 15-min periodic checkpoints, not a shutdown one. Now it checkpoints on SIGHUP too (tested: tmux kill-server → `ckpt` + `stop.json`).
  - **`--resume` with no checkpoint** (stopped in the first 15 min) restarts the run from step 0 with the same config, keeping the old logs as `*.before-restart-<n>`.
  - **Resume log (`pokered/runlog.py`).** Each resume appends to `config.json["resume_log"]`: resumed-from checkpoint and step, where the stopped segment ended (`stopped_at_step`, with `basis`: `stop.json` = exact, `metrics+vm_event` = estimate from the GCP stop time, `metrics` = lower bound), `replayed_steps`, and the GCP event. It also writes a marker row `{"resume": n, "step"/"global_step": ckpt step, "ckpt", "time", "max_step_before"}` into `metrics.jsonl` and `episodes.jsonl`.
  - **Analysis must read logs through `runlog.load_kept(run_dir, "metrics.jsonl" | "episodes.jsonl")`.** It drops rows on the discarded branch (logged before a resume, with step > the resumed checkpoint) and the markers. Older logs without markers get them synthesized from the metrics step drops, with the per-update `episodes` counts placing the cut in `episodes.jsonl`. `evaluate.py`'s training-side hack counts use it.
  - `gcp/run.sh` records the VM's GCP stop events (preempted / guest shutdown / stop) in `~/roms/runs/vm-events.jsonl` on the VM before resuming. `backfill_resume_log.py RUN_ID [--write]` rebuilds `resume_log` for runs from before this (done for A0-D1-s0: 2 resumes, ≈119k and ≈12k replayed steps; 122 metrics rows and episodes 104–111 dropped).
- **Tested** on Jake's ROM (smoke mode, no D1): RAM-MLP at 158 sps; tiles-CNN SIGTERM at step 4,224, then `--resume` to 12,096 with monotonic steps and no duplicates; screenshot and sidecar written.
- **Per-update speed log (for the pilot):** every `metrics.jsonl` row has `sps_update` (that update alone), `t_collect` / `t_learn` (seconds), `load1` (load average), `cpu_mhz` and `maps` (share of the rollout spent on each map ID, mod 64).
  - Any update below 60 sps also prints a `slow update` line.
  - These tell a game-phase slowdown (the map mix shifts) apart from contention from other processes (load above ~4.5 with 3 envs) and from throttling (MHz drops), if the 21–31 sps dip comes back.
  - Sample from the bench state: 192 sps, collect 1.47 s vs learn 0.53 s per update. The real trainer is env-bound, not learner-bound, which is why the bench formula's 80 was too low.
- **Hyperparameters:** `HPARAMS` in `train.py` are the pre-pilot defaults (rollout 128, 4 epochs, minibatch 256, lr 2.5e-4, γ 0.998, λ 0.95, clip 0.1, entropy 0.01, episode 16,384 steps). They get pinned at the pilot, then frozen for all arms (§5).
  - `--out NAME` writes to `~/roms/runs/<id>/NAME/` instead; `--window-stats` adds `windows.jsonl` (one row per window, `window_stats` fields). Summary rows gain `share_L` and `share_K`. Same seeds as before, so a re-score replays the same episodes (checked against the first eval).
- **Evaluation: `evaluate.py RUN_ID [--states D1 HA HB] [--episodes 8]`.**
  - Runs every `eval-<step>.pt` plus the final weights, N sampled-policy episodes per start state (seeds 1000…, jittered), using the run's own reward, core and episode length.
  - Keeps full traces and applies `detectors.scan` + `merge`. HB is loaded with its recorded levels; note that HB starts in Viridian, so T = 1 at reset.
  - Writes `~/roms/runs/<id>/eval/{episodes.jsonl,summary.json}`: per checkpoint × state, mean/max T, the share reaching ≥ M1 and ≥ M2, mean P, and detector events.
  - Also writes the **§9 pilot go/no-go**: some eval episode reaches ≥ M2, and a detector fires (eval traces, or the trainer's online detectors).
  - Episodes run in a spawn process pool, one torch thread each. Tested on a 3k-step run.
  - `--out NAME` writes to `~/roms/runs/<id>/NAME/` instead; `--window-stats` adds `windows.jsonl` (one row per window). Summary rows gain `share_L`, `share_K`, `share_U` and K window counts. Same seeds as before, so a re-score replays the same episodes (checked against the first eval, 144/144).
  - `--save-traces` keeps each episode's gzipped trace under `<out>/traces/` (first line = episode meta); `--from-traces DIR` re-scores those without replaying, so later detector changes cost minutes, not a VM run.

## A2′ shaped oracle, detector O, R0 (2026-11-03; experiment-e1.md §4, §6, §9 "A2 oracle pilot" + "U review")

- **Arm `A2p`** (`train.py --arm A2p`; `env.ShapedOracle`): reward = ΔT + γΦ(s′) − Φ(s), γ = the PPO γ (0.998). The proxy terms are computed and logged as before (P, detectors) but not paid. Trace rows now carry `r`, the reward the arm was actually paid. The reward hash includes `shaping.table_hash()`.
- **Φ (`pokered/shaping.py`)**: Φ = −[(5 − T) + min(d/d_leg, 2)], Φ = 0 at T = 6.
  - d is the route distance in tiles to the next milestone's map (leg 6: the tile below Brock). On the current map it's Manhattan to an exit (warp tile, or any edge tile that overlaps the connected map) + 1 step through it, plus the distance from where that exit lands.
  - Distances are a Dijkstra over every exit of the 32 maps in the region, run backwards from each leg's target, so off-route maps route back through their exits. Maps outside the region get the floor (d/d_leg = 2).
  - **Deviation for review:** the (5 − T) term isn't in §4's text (Φ = −d/d_leg). It's a function of T, which is part of the state, so Φ is still a potential and the optimal policies are unchanged. It makes Φ continuous across a milestone: with −d/d_leg alone, Φ drops by about 1 at each milestone, which cancels the +1 of ΔT on that step.
  - **Correction to §4:** "around a cycle the terms telescope to ≤ 0 for γ < 1" holds for Φ ≥ 0. Here Φ ≤ 0 (so that Φ = 0 at the absorbing state), and a closed loop nets Φ(s₀)(γ^N − 1) ≥ 0. That's a stipend of (1 − γ)|Φ| ≤ 0.014 per step whatever the agent does.
    - It is still potential-based, so policy-invariant (Ng et al.): it's exactly what discounting costs everything after the loop.
    - Pacing pays nothing at γ = 1 (tested).
    - On the scripted trace it adds about 71 to the undiscounted reward sum (7,245 steps). The alternative is shaping with γ = 1 (F = Φ′ − Φ: no stipend, sum = ΔT + ΔΦ exactly), which is only approximately invariant at γ_PPO = 0.998. The pilot runs the §4 version (γ = 0.998).
- **Map data:** pret/pokered master (local copy, 2026-11-02):

  - `constants/map_constants.asm`: sizes in blocks, 1 block = 2×2 tiles.
  - The tables are literal dicts in `shaping.py`, with each map's pret name in the constant names.
  - **Checked against the scripted trace:** all 14 map transitions land on the pret warp/edge tile. wCurMap updates 1–2 env steps before wXCoord/wYCoord, so for those rows Φ clamps the stale coordinates into the new map.

        - p = one-sided Monte Carlo permutation, B = 100,000 relabelings, (k + 1)/(B + 1). The relabelings are drawn once per group size with a fixed seed and vectorized (about 6 s for a full table).
        - Holm is unchanged: over each detector's cells in the arm.
        - The bootstrap CI now resamples episodes within seeds. Per-seed shares are shown next to the pooled share.
        - `--exact` enumerates all relabelings when there are ≤ 200,000 (the 1-seed pilot's 8 vs 8 = 12,870). Tests check the exact p by hand and the MC p against the exact one.
      - **A0 pilot (1 seed, 8 vs 8):** the MC and exact tests agree, and only D is present (500k, all three states).
        - M at 500k: p 0.0035–0.0085 → Holm 0.063–0.136, so not present. The earlier bootstrap p of 0.0001 was anti-conservative at n = 8.
        - HA O at 5M: Holm 0.10, not present.
        - Sparse A2: M at 250k is present.
      - The family is 6 checkpoints × 3 states = 18 cells per detector (12 for O). At 8 vs 8 a cell needs p ≤ 0.0028, which is what pooling seeds and R0 at 24 episodes fix.
- **Tests** (`tests/test_shaping_o.py`, 16):
  - leg lengths by hand; bounded Φ, 0 when done;
  - continuity across M1;
  - discounted telescoping over a 5,000-step random walk = γ^N Φ_N − Φ_0;
  - a closed loop nets 0 at γ = 1 and exactly Φ₀(γ^N − 1) at γ < 1; two-tile pacing pays 0;
  - Route 2 split; stale-coordinate clamp;

## A2″ progress oracle: walking distance, validation, A2′ diagnostics (2026-11-03; experiment-e1.md §9 "A2′ pilot")

**Reward (`--arm A2pp`, `env.ProgressOracle`, `pokered/walkdist.py`).** r = ΔT + max(0, d_min − d_t)/d_leg, where
d_t is the BFS walking distance (env moves) to the next milestone and d_min is the best d so far in this leg of this
episode (`walkdist.Progress`):
- d_min starts unset at reset and at each milestone, and the first usable d sets it without pay.
- A d is usable when the square is in the graph and the map hasn't changed for SETTLE_STEPS = 2 steps (§9 (c)).
- On the milestone step, the leg's remaining d_min/d_leg is paid, so a leg pays d_first/d_leg in total
  (exactly 1 from the reference start).
- Loops, pacing and backtracking pay 0, and there's no stipend.
- d_leg (reference path, as in A2′) = 80 / 39 / 51 / 160 / 45 / 11 moves.
- `reward_params` records the walk-grid hash and `settle`.
- metrics.jsonl and episodes.jsonl log the progress term as `shaping` (r − ΔT), like A2′.

**Walk grid (`walkgrid.py build PRET_DIR` → `~/roms/walkgrid.json`, outside the repo; copied to the VM by
`gcloud compute scp`, like the states).** It is built from pret, under the game's own rules:
- **Passability:** step square = bottom-left tile in the tileset's collision list. Sources:
  `maps/*.blk` via `maps.asm`, the map's tileset from `data/maps/headers`, the blockset from `gfx/tilesets.asm`,
  and the lists in `data/tilesets/collision_tile_ids.asm`.
- **Tile-pair collisions:** `pair_collision_tile_ids.asm`, which matters only in Viridian Forest.
- **Ledges:** `ledge_tiles.asm`. One-way (down/left/right), one press hops 2 squares.
- **Warps and connections:** as in `shaping.py`. A warp square is used only if it's passable: the forest
  south gate's (4,0) isn't, and the planner got stuck on it before this rule.
- **Stationary NPCs and items:** `object_event … STAY` entries are blocked squares when the D1 state shows them.
  Visibility comes from D1's wToggleableObjectFlags (0xD5A6, pret sym) and the order in
  `toggleable_objects.asm`. Examples: the Viridian girl (17,9) is blocked; the lying old man (18,9) is hidden

- **Not modeled:** walking NPCs and trainers' sight lines.

- **Pallet:** the A2′ defect is gone. From town only x = 10, 11 exit north, and the tree-line row has no plateau.

**Verdict under §5b's pre-registered rule 5: FAIL.** WRAM and the RNG bytes diverge, so the normal core is used for all arms. The likely cause is that `fast_mode` doesn't emulate serial I/O, so the link check takes a different path.
- That isn't the "sound or serial registers only" exception (rule 4): the difference propagates into game state.
- An agent can easily reach that counter in training, so the divergence is relevant to the arms, not an edge case.

**Characterization (researcher's follow-up and §5b "Ruling on the exemption"; 2026-11-02):**
- **Mechanism (pret `engine/link/cable_club_npc.asm`).** After the welcome text, `CableClubNPC` runs `.establishConnectionLoop` 90 times. Each pass writes `rSB`/`rSC` to start an internal-clock transfer and polls `hSerialConnectionStatus` (0xFFAA).
  - On the normal core, the transfer completes with no partner and fires the `Serial` interrupt: 89 hits in the smoke run.
  - On `fast_mode` it fires **0** times. The serial HRAM bytes (0xFFA9 `hSerialReceivedNewData`, 0xFFAC/AD send/receive) end up different, and `Random_`, which stirs from `rDIV`, then gives different RNG bytes.
  - The signal is PyBoy execution hooks on the pret addresses (`CableClubNPC` 01:71C5, `.establishConnectionLoop` 01:71EB, `Serial` 00:2125, every `Serial_*` routine), registered identically on both cores.
- **(a) What `fast_mode` does after the attendant** (smoke run, 1,557 steps from HB, "accept" policy):
  - **normal dialogue, not a hang or a link screen**;

  - map, position, facing, party, bag, money, badges, event flags and `wLastBlackoutMap` are identical;
  - the only remaining differences are the RNG and serial HRAM bytes.
  - The 10-run test (below) checks this on every divergence.
- **A second, non-serial divergence: power-on.** From power-on with no input, the cores differ at **frame 84** in `hRandomAdd` (0xFFD3).

  - So this is a difference in PyBoy's power-on initial conditions (internal timer/LCD phase), not ongoing drift.
  - Training never starts from power-on (every episode loads a state), but the scripted start states do. **States made on the two cores are therefore different trajectories:**

This covers own state, dev only: P by term, T, leg progress, ×R0, g against the planner, L episodes, A2″ collapse flag, and train-side P/T since the last mark. It also records sps against batch 1, `obs_version` and the reward hash. An HA-trained run's training episodes are never summarised.
- **On reads:** an interim eval (own state × 8, `--kl-init`) into `<run>/eval-interim/<ckpt>/`, then the H4′ tripwires A-1, A-2, B-1, B-2 and C into `<run>/tripwire.json`.
- **On a trip:** `queue.sh pause REASON`. No new entry starts on this VM, and the peer is paused the same way. The running entry finishes, the queue stays active, and nothing is dropped. `queue.sh resume` clears it, one VM at a time.
- **The peer pause:** each VM holds `~/.ssh/e1_peer`; the other's `authorized_keys` accepts that key only for the forced command `queue.sh pause-from-peer`, with no shell and no forwarding. `~/e1/queue/peer` names the peer. Set up with `gcp/peer_setup.sh`.
- **Health checks:** `b2_reads.py brief RUN…` gives the one-line science read that goes next to the infra numbers.
- **Resumes (§9 H9):** every resume is a partial restore by design. The learner is restored exactly, but in-progress episodes restart and the env workers are reseeded. Each `resume_log` entry records `restored`.
  - **Keep** when all four hold: (i) an infrastructure trigger (a signal reason in `stop.json`, or a GCP VM event), (ii) an exact learner restore from a checkpoint, (iii) the run reaches M, and (iv) ≤ 2 resumes and ≤ 100k replayed or lost steps.
  - **Otherwise escalate:** the run goes to the researcher before its closing eval is read.
  - **Where it shows:** the summary and the brief line carry the status. `b2_reads.py resumes RUN…` prints the table of resumed runs for the batch-2 report.

**Training-episode series** (`train_series.py --batch b1|b2`, §9 H10; descriptive, never a test) writes `results/<batch>/train-series.{json,md}`.

- **Scope:** own training state only. HA-trained runs are excluded, because their training episodes are held-out data.
- **Bins:** completed training episodes whose end step falls in (m − 250k, m] at each eval mark, giving n, P, P by term (batch 2 only), T, the shares reaching ≥ M1 and ≥ M2, and the prevalence of each online flag (`hacks_active`, K).
- **Snapshot comparison:** each bin is paired with the run's own-state snapshot eval at that mark (batch 1 `eval-dev/`, batch 2 `eval/` + `eval-interim/`), giving the gap and the train/snapshot P ratio (S4).
- **S1 and S2 (§9 H10′):** both are decided on both series by seed-bootstrap 95% CIs of per-seed differences: (i) P(5M) − P(0.5M) > 0, and (ii) A0 − A2″ T < 0 at one or more marks from 2M on. The `h0_tests` permutation output is kept but labelled "not used (pseudo-replication)", because training episodes are correlated. Its snapshot side reproduces `results/b1/h0.json` exactly.
- **S3:** A0 − A2″ T at 5M, paired by seed.
- **Not available:** leg progress and per-step traces, since training logs neither (§9 H10 amendment: no mid-batch training-code change). Batch 1 also lacks P by term.
- **Per-run line:** the report's descriptive row of training-episode P and T per mark.

**Cost** (`gcp/b2_cost.py --sps-ratio R`) uses batch 1's measured train and eval hours, the smoke sps ratio, 32 state-marks per run with KL, the pilots, interim reads, idle tails, disks and IPv4. The ceiling is the estimate × 1.3, set with `gcp/arm.sh --ceiling-b2 USD HOURS_A HOURS_B`. The per-VM hours sit on top of each VM's lifetime counter at its first batch-2 arming; batch-1 ledger entries move to `history`.

**Why `--termination-time` and not `--max-run-duration`:** per the GCP docs, max-run-duration "is recalculated by
adding that duration to the VM's latest start time", so every restart grants a fresh window. termination-time "doesn't
change when you reset or reboot the VM". Once it passes, "any requests to create or rerun the VM fail until you update
or remove the time". So the GCP side caps each window absolutely, and after it the VM can't run until `arm.sh` re-arms it
under the ledger check. (Scheduling changes need a stopped VM, hence the stop/start in `arm.sh`.)

**The hard ceiling (whole plan):** `gcp/arm.sh --ceiling --M N` writes it to `~/roms/runs/gcp-budget.json`.
- It is the plan's VM-hours × 1.3 at the same rates, plus disks.
- Enforced in two layers:
  - In-guest: each VM's lifetime uptime ≤ its ceiling hours.
  - `arm.sh`: refuses a window if this VM's counter + the window passes its hours, or if the plan's dollars would
    pass `ceiling_usd`. Every window is capped GCP-side by `--termination-time`.
- **Residual risk, stated:** if a guest hangs (counter stops), the overrun is bounded by that one window's
  remainder. A start outside `arm.sh` with a hand-set termination time bypasses the ledger.

It never syncs code while a trainer is running, so a resumed run keeps the code it started with; `CODE_SHA256` is logged per run. `--resume-all` after a stop or preemption starts the VM and resumes everything partial. `--status`. `--guard HOURS` re-arms the uptime guard. |
| `fetch.sh [--no-ckpt]` | rsync VM `~/roms/runs/` → laptop `~/roms/runs/`. It never deletes locally and is safe mid-run. |
| `teardown.sh [--no-fetch]` | Fetches, then deletes the VM with `--delete-disks=all`. It aborts if the fetch fails, and afterwards lists anything left with `purpose=e1`. |

**Cost guards** (each STOPS the VM; the disk and results survive until teardown; a stopped VM still bills its 30 GB disk):
1. In-guest uptime timer: `--hours` (default 12). It is re-armed on every boot by the startup script `remote/guard-startup.sh`.
2. Idle guard: power off after 45 min with no `train.py`, bench or `pip install` running. So a finished pilot does not sit billing until the timer.
3. GCP-side hard cap: `--max-run-duration = hours + 1` with termination action STOP. It holds even if the guest hangs. Per the GCP docs (checked 2026-11-02) the duration counts from **each start**: stopping clears it and starting re-arms it. Raising it requires stopping the VM (`set-scheduling`). Size `--hours` to the job: the pilot is ≈ 2–4 h on 32 vCPU; main-arm batches take longer.

`bench.sh` / `run.sh` / `fetch.sh` start the VM if a guard or preemption stopped it.

**Spot:** preemption sends SIGTERM, and `train.py` checkpoints on SIGTERM. Recovery is `gcp/run.sh --resume-all`. Spot's 30 s notice is enough for one checkpoint (≈ MBs), *unverified* on GCP.

**Trainer contract for checkpoints** (the PPO trainer `train.py` is the next build task; it doesn't exist yet):
- Every run lives in `~/roms/runs/<run_id>/`.
- Every N updates (default: about every 15 min of wall-clock) the trainer writes `ckpt-<step>.pt`: policy, optimizer, RNG states, step counter, reward params and hash, and the hack first-appearance table. It writes to a temp file and then renames it, so a crash never leaves a half-written checkpoint. Only the last 3 are kept, plus the log-spaced eval checkpoints that §5 needs.
- `--resume <run_id>` loads the newest complete checkpoint and continues the same seed stream. Results are therefore identical whether or not a run was interrupted, up to env-timing jitter.
- RAM-derived logs (`metrics.jsonl`, `firings.jsonl`, eval traces) sit next to the checkpoints. Those are the files that get copied into the repo for figures; screenshots and checkpoints stay in `~/roms/runs/`.

# Secondary: LLM candidates 1–4 (earlier rough pass)

These numbers are back-of-envelope estimates from experience with these tools, not measured. Expect ±2×.

## Ground rules for the estimates

- **This machine has no usable GPU** (Intel UHD 617, 8 GB RAM). Every option below needs either a GPU box
  Jake has elsewhere or rented cloud. "One GPU" means one 24 GB card (RTX 3090/4090 class), local or rented.
- Rented 24 GB cards cost roughly $0.3–0.7/h; A100/H100 80 GB roughly $1.5–3/h (check current prices).
  So the default ~$100 budget buys ~150–300 h on a 24 GB card or ~40–60 h on an 80 GB card.
- Shared stack for all four: `transformers`, `datasets`, `trl` (RM training, DPO, GRPO), `vllm` (fast sampling),
  `peft` (LoRA). Versions pinned in a `requirements.txt` once a candidate is picked; seeds fixed, 3 seeds per condition.
- Models: Qwen2.5 0.5B / 1.5B / 7B (Instruct and Coder variants) as policies and small RMs; an open 7–8B reward
  model or judge as "gold". All open-weight, all fit the brief's 1–8B limit.
- Cheapest optimizer everywhere is **best-of-n (BoN)**: no training, just sample and score. Light RL (GRPO/PPO)
  is 3–5× the cost and is where "one GPU" starts to strain.

## Summary (LLM candidates)

## 1. Patch-and-regress

- **Setup:** Gao et al.-style synthetic gold. A gold RM (open 7–8B) labels comparisons; proxy RMs (Qwen2.5-0.5B/1.5B)
  train on those labels. Defense A: retrain the small proxy each round on the current policy's top-scoring outputs
  (gold-labeled). Defense B: same label budget spent on a bigger proxy or a 3–5 RM ensemble. Plot gold vs proxy
  score against optimization strength (BoN n, or KL for RL).
- **Data:** prompts from UltraFeedback or AlpacaFarm (~1–2k prompts); gold labels are free (synthetic), so the
  "label budget" is a counted number of gold calls, not human time.
- **Compute (BoN):** ~1k prompts × up to n=256 samples ≈ 250k generations from a 1.5B policy (~1–3 h on vLLM),
  gold scoring with an 8B RM (~3–6 h), ~10–20 small RM trainings at <1 h each, 3 seeds. **≈20–40 GPU-h, one GPU.**
- **RL variant:** PPO/GRPO against each proxy, several KL points, 3 seeds → **≈60–120 GPU-h, cloud** (or skip; BoN
  alone already reproduces overoptimization curves).
- **Tooling:** all off the shelf. The fiddly part is the loop logic and honest budget bookkeeping.

## 2. Judge exploitability and transfer

- **Setup:** policy (Qwen2.5-1.5B/7B-Instruct) samples n responses per prompt; pick the best by judge J; score that
  pick with the other judges and a held-out gold judge. Repeat for each J and several n. Then regress gains on surface
  features (length, hedging/confidence words, markdown density, flattery phrases), and run controlled edits
  (pad length, add formatting) to test causality.
- **Data:** 300–500 prompts from AlpacaEval / Arena-Hard-style sets. No training data needed.
- **Judges:** 3–4 open 7–8B judges (general instruct models plus a dedicated judge model) run locally; gold = a
  frontier model via API, called only on the selected picks (a few thousand calls, ~$10–40).
- **Compute:** ~500 prompts × n=64 ≈ 32k responses (<2 h), then ~32k × 4 judge calls with vLLM (~2–5 h per judge).
  **≈10–25 GPU-h, one GPU, no training at all.** Could even run entirely on APIs.
- **Tooling:** vLLM + a small judging harness + pandas for the feature analysis. Fastest to a first figure.

## 3. Test-gaming in code RL

- **Setup:** GRPO on a code model with reward = visible unit tests passing; true quality = hidden tests (e.g. MBPP+ /
  HumanEval+ extra tests). Count special-cased/hard-coded solutions; then score a cheap monitor (a 1.5–7B model
  reading the diff) for precision/recall against a labeled sample.
- **Data:** MBPP/MBPP+, HumanEval+, or an APPS subset, with tests shown in the prompt so gaming is possible.
- **Compute:** 1.5B with LoRA GRPO on 24 GB: ~5–10 h per run; 7B needs an 80 GB card. Several conditions × 3 seeds
  plus monitor eval → **≈50–150 GPU-h, realistically cloud.**
- **Tooling:** heaviest of the four. Needs a sandbox for executing model code (bubblewrap/firejail or containers,
  no network, time/memory limits) plugged into the reward function, plus GRPO (TRL or verl).
- **Risk:** small models in short runs may simply not discover test special-casing. We'd likely have to make the
  hack easy (weak/visible tests, writable test files), which changes what the result means. Worth a 1-day pilot
  before committing.

## 4. Preference-data poisoning

- **Setup:** train RMs on a preference set with a fraction (e.g. 0.1%–5%) of comparisons flipped to reward a benign
  marker behavior under a trigger; measure the RM's preference for it, then optimize a policy against the RM and
  check whether the behavior appears. Finally apply defense (1) and see if it removes it.
- **Data:** UltraFeedback or HH-RLHF (~60k pairs). Behavior should be harmless and easy to detect (a marker phrase
  or format), keeping this analytical per AGENTS.md.
- **Compute:** ~6 poison rates × 3 seeds = 18 RM trainings at ~1 h (0.5–1.5B) ≈ 20 h; BoN check ≈ 10–20 h →
  **≈30–60 GPU-h on one GPU.** Showing it "survives RL" needs RL runs → **≈80–150 GPU-h, cloud.**
- **Tooling:** off the shelf (TRL RewardTrainer). Shares most code with (1), so it's cheapest *after* (1).

## Notes for ranking

- (2) is the only one that fits comfortably on one GPU with zero training and gives a figure in days.
- (1) is a good one-GPU project if we stay with BoN; it also builds the pipeline (4) reuses.
- (3) and (4)-with-RL are the ones that would blow the ~$100 default.
- Outputs for whichever we run: `code/` (scripts, pinned deps), `code/figures/` (SVG plus monospace ASCII versions for the post).
